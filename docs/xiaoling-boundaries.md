# 小灵 AI 边界基线

状态：草案基线

适用分支：`develop` 及其 `codex/*` 产品分支

Kun 基线：`xiaoling-base-kun-v0.3.10`

## 目的

小灵 AI 以 Kun 作为可演进、可替换的 Agent 底座。我们可以修改 Kun，也可以
把通用能力补回底座；边界要求的是不要让产品策略、渠道逻辑和底层实现形成
不可分离的耦合。本文先冻结所有权、分支、接入面和同步规则，不定义具体功能、
界面或客户端实现。

本文是边界规则，不是完整架构设计。任何新功能都必须先说明它属于哪一层，
以及为什么不能通过现有适配器或扩展边界实现。

## 产品身份与代码归属

最终交付物、仓库、用户界面、版本发布和产品责任主体都是小灵 AI。Kun 只是
当前部分代码的来源和可同步的上游基线，不是最终产品形态，也不是需要永远
原样保留的第二个产品。

因此，保留或改造 Kun 代码都属于小灵 AI 的工程演进：所有代码都接受小灵 AI
的测试、审查、发布和扩展规则。对于仍来自 Kun 的代码，只额外保留来源、上游
同步和许可证信息；这属于工程溯源和法律义务，不改变小灵 AI 的产品身份。

## 当前范围

当前阶段只交付以下边界资产：

- 产品与底座的所有权图；
- 分支和 Kun 上游同步规则；
- 可插拔接入面的约束；
- 共享协议的概念清单；
- 许可证与商业授权记录入口。

当前阶段不实现：

- 手机端或微信端功能；
- 新的桌面工作流或 UI；
- Office、浏览器自动化、计费和多租户；
- 新的 Agent Loop、模型路由或持久化系统；
- 竞品功能的直接移植。

## 分支与版本边界

```text
upstream/master
      |
      v
codex/sync-kun-vX.Y.Z  -- 只处理一次 Kun 上游同步
      |
      v
develop                -- 小灵 AI 集成分支
      |
      +--> codex/<feature>  -- 单个产品改动
      |
      v
main                   -- 可发布版本
```

- `main` 只接受可发布、已验证的小灵 AI 版本。
- `develop` 是产品集成分支，不直接承载未验证的功能改动。
- 新开发从 `develop` 创建 `codex/` 前缀分支，并通过 Pull Request 合入
  `develop`。
- `upstream` 只用于读取 Kun 上游，不在上游远程上开发小灵 AI 产品代码。
- 上游同步和产品功能使用不同分支、不同提交和不同 Pull Request。
- Kun 快照标签使用 `xiaoling-base-kun-vX.Y.Z`；小灵 AI 产品版本使用
  `xiaoling-vX.Y.Z`，两者不能混用。

本分支只记录边界规则。第一份功能实现必须从后续的 `develop` 状态重新创建
功能分支，不能把功能顺手追加到本分支。

## 三类来源与维护边界

### Kun-derived 区（来源分类）

Kun runtime、线程与事件实现、工具执行、通用桌面工作台和现有扩展平台属于
Kun-derived 区。该区域不是只读区：如果缺少的是对所有产品和客户端都通用的
runtime 能力，可以在这里修改或新增扩展点。目标是让修改可解释、可测试、可
回放，便于按版本同步上游。

对该区域的必要修改必须满足：

1. 修改属于通用 runtime 能力、正确性、安全性、性能或上游缺陷修复，而不是
   某一个渠道的产品策略；
2. 能通过清晰的 port、contract 或 extension point 暴露，不把调用方绑定到
   隐藏实现；
3. 记录基于哪个上游提交、影响哪些文件和兼容条件；
4. 修改尽量是可独立回放的小 patch，并配套行为或兼容性测试；
5. 上游同步出现冲突时，重新评估能否下沉为通用能力或外移到适配器，而不是
   默认扩大核心差异。

### Xiaoling-owned 区（产品改造）

小灵 AI 自有代码负责品牌和产品策略、账号与权限、渠道连接器、运营审计、
商业策略以及未来的产品差异化能力。小灵 AI 可以改造 Kun 的 Agent Loop、线程
存储或模型客户端；但直接加入渠道特判和商业流程会形成难以同步的耦合，默认应
放在适配器或产品模块中。若产品形态确实要求底座改造，应通过 ADR、契约和测试
说明为什么它属于小灵 AI 的核心能力。

自有代码的具体目录在首个功能确定后再按模块建立；本阶段不提前复制 Kun 目录
或创建一套平行 runtime。

### Shared contract 区

以下能力是客户端、适配器和 Kun runtime 之间的共享契约：

- Thread / Turn：任务、续跑、取消、恢复和来源 surface；
- Event / SSE：有序事件、序列号、重放和断线恢复；
- Approval / UserInput：高风险操作和结构化用户输入；
- Artifact / Attachment：文件、产物和引用的生命周期；
- Auth / Capability：身份、工作区、线程权限和可用能力；
- Extension / Adapter version：能力版本和兼容范围。

共享契约的改变必须有兼容性说明、测试和 ADR。客户端不应通过读取 Kun 内部
对象来绕过这些契约。

## 可扩展性原则

可扩展性不是把所有代码都移到插件目录，而是让变化沿着稳定边界传播：

- **依赖方向**：产品模块依赖版本化契约，适配器依赖 runtime port，具体实现
  可以替换；底座不依赖微信、手机或某个商业产品策略。
- **能力可选**：客户端通过 capability/version 判断是否支持某能力，不能假设
  所有 runtime 都具备同一组可选扩展。
- **扩展可隔离**：单个扩展或通道的失败、升级和停用不应破坏核心 Thread、
  Event 和 Approval 状态机。
- **通用优先**：当一个能力对多个客户端都成立时，可以进入 Kun-derived 区；
  当它只服务一个产品流程或渠道时，优先放在 Xiaoling-owned 区。
- **可替换实现**：适配器和扩展不应把内部类、文件布局或桌面组件当成协议；
  需要稳定依赖时，先把它提升为明确的 contract。

## 可插拔接入原则

优先使用 Kun 已有的 HTTP/SSE runtime、Extension API、MCP 和 Skills 等公开
接入面。当这些接入面缺少通用能力时，可以先在 Kun-derived 区补充版本化的
port 或 contract，再由适配器使用。以下内容默认不是小灵 AI 的稳定扩展面，除非
经过 ADR 明确提升为版本化契约：

- Agent Loop 的内部函数和未声明的内部模块；
- Electron 私有 IPC、`window.kunGui` 和 renderer store；
- DOM、CSS 选择器和桌面窗口抓取；
- 未版本化的私有 RPC 或本地 bearer token。

桌面、手机、微信和其他 IM 都是同一 Thread/Event 能力的不同 `clientSurface`。
通道适配器只负责：提交任务、订阅事件、转发审批和用户输入、处理附件与产物、
取消或重试，以及身份和权限映射。

“查看桌面对话”应通过事件、线程快照和产物协议完成，而不是抓取桌面 UI。
远程通道必须经过认证 API 或网关，按用户、工作区、线程和 capability 授权，
并保留 Kun 的 approval 约束。微信或手机不能被视为可信执行环境。

## 上游同步边界

按 Kun release 或明确的上游版本批量同步，不对上游零散提交持续 cherry-pick。
每次同步都应经过独立同步分支、差异检查、兼容性检查和最小验证门禁，再合入
`develop`。详细步骤见 [`upstream-sync.md`](./upstream-sync.md)。

需要长期保留的产品差异应移动到 adapter 或 extension 层。只有无法通过公开
接入面实现、且对所有产品客户端都成立的底层修复，才考虑进入 Kun-derived 区。

## 变更门禁

提交前必须回答：

1. 这项改动属于哪一个来源/维护分类？
2. 是否依赖了未承诺稳定的 Kun 内部实现？
3. Kun 更新后，改动是否可以单独回放、通过通用契约保持兼容，或被适配器吸收？
4. 是否扩大了某个客户端的权限或绕过了 Approval/Capability？
5. 是否需要更新共享契约版本、兼容测试或许可证记录？

如果答案不清楚，先补充 ADR 或边界说明，不直接开始功能实现。
